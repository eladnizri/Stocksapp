# מי מפעיל את בדיקת ההתראות

## הבעיה, בשורה אחת

`on: schedule` ב-GitHub Actions הוא **best effort** לפי התיעוד של GitHub עצמם.
הוא יכול להתעכב או פשוט לא לקרות, בלי שגיאה, בלי אימייל, בלי ריצה כושלת —
כלום. זו לא ריצה שנכשלה, זו ריצה **שלא נוצרה**, ולכן אין מה לבדוק ואין למי
להתלונן.

בפרויקט הזה זה קרה לפחות פעמיים:

| מתי | מה קרה |
|---|---|
| סוף אוגוסט | שלושה ימים רצופים בלי אף טיק, דרך יום מסחר שלם |
| 1 בספטמבר | פער של ~21 שעות; דוח ה-17:00 לא נשלח כי אף ריצה לא קרתה בשעה הזו |

הזזת הדקות מ-`*/15` ל-`3,18,33,48` (בהמלצת GitHub, כי השעות העגולות הן
זמני העומס שלהם) **נוסתה ולא הספיקה** — שלושה טיקים רצופים אחריה לא ירו.

## הפתרון: טריגר חיצוני

הבעיה היא ב**טריגר**, לא בעבודה. הריצות עצמן, כשהן קורות, עובדות מצוין —
כל ריצה ידנית בהיסטוריה הצליחה. אז במקום להסתמך על המתזמן הפנימי של GitHub,
שירות חיצוני קורא כל 15 דקות ל-API שמפעיל את אותו workflow בדיוק.

ההבדל המהותי: קריאת API היא בקשה עם תשובה מיידית — או `204 No Content`
(עבד), או קוד שגיאה **שרואים בלוג**. אין מצב של היעלמות שקטה.

```
cron-job.org  ──POST──>  GitHub API  ──>  alerts.yml  ──>  ntfy
   (כל 15 דק׳)            (204 מיידי)      (ריצה רגילה)     (הטלפון)
```

הקוד, הסודות וקובץ המצב לא זזים לשום מקום. רק מי שלוחץ על הכפתור.

# ההקמה

## שלב 1 — טוקן GitHub עם הרשאה אחת בלבד

`Settings` → `Developer settings` → `Personal access tokens` →
**Fine-grained tokens** → `Generate new token`

- **Token name:** `cron-trigger`
- **Expiration:** שנה (רשום ביומן להחליף — ראה "כשהטוקן פג" בהמשך)
- **Repository access:** `Only select repositories` ← בחר **Stocksapp** בלבד
- **Permissions** → `Repository permissions` → **Actions: Read and write**
  (זו ההרשאה היחידה שצריך. `Metadata: Read-only` נוסף אוטומטית)

העתק את הטוקן — הוא מוצג פעם אחת בלבד.

> **זה לא הטוקן של האפליקציה.** לאפליקציה בטלפון יש טוקן נפרד עם הרשאת
> `Contents`, והוא חי ב-localStorage של הדפדפן. אל תשתמש באותו טוקן לשניהם
> ואל תרחיב את זה שכבר קיים: לכל אחד תפקיד אחד, וכך דליפה של אחד לא נותנת
> את היכולות של השני.

**מה טוקן כזה יכול לעשות אם ידלוף:** להפעיל ולבטל workflows בריפו הזה בלבד.
הוא לא יכול לדחוף קוד, לקרוא ריפו אחר, או לשנות משהו בחשבון. הריפו ממילא
ציבורי. הנזק המקסימלי הוא הצקה, והביטול הוא לחיצה אחת ב-GitHub.

## שלב 2 — חשבון ב-cron-job.org

https://console.cron-job.org — הרשמה עם מייל. חינם, בלי כרטיס אשראי.

## שלב 3 — יצירת ה-job

**Create cronjob**, ואז:

### לשונית COMMON

| שדה | ערך |
|---|---|
| **Title** | `Stocksapp alerts` |
| **URL** | `https://api.github.com/repos/eladnizri/Stocksapp/actions/workflows/alerts.yml/dispatches` |
| **Execution schedule** | ראה למטה |

**Execution schedule** — בחר `Custom`:

- **Timezone:** `UTC` ← חשוב, לא שעון ישראל
- **Days of month:** every
- **Months:** every
- **Days of week:** Monday–Friday בלבד
- **Hours:** 13, 14, 15, 16, 17, 18, 19, 20, 21
- **Minutes:** 3, 18, 33, 48

זה בדיוק אותו חלון שה-workflow משתמש בו היום: 13:00–21:59 UTC מכסה את שעות
המסחר האמריקאיות גם בקיץ וגם בחורף, וגם את שעת הדוח (17:00 בישראל).

### לשונית ADVANCED

**Request method:** `POST`

**Headers** — שלוש שורות:

| Name | Value |
|---|---|
| `Accept` | `application/vnd.github+json` |
| `Authorization` | `Bearer ‹הדבק כאן את הטוקן משלב 1›` |
| `X-GitHub-Api-Version` | `2022-11-28` |

**Request body:**

```json
{"ref":"main"}
```

**Treat redirects with HTTP 3xx as success:** לא משנה
**Enable job:** ✔

### לשונית NOTIFICATIONS — אל תדלג על זה

סמן **"Notify me when the job fails"**.

זו הנקודה הכי חשובה בכל ההקמה. כשהטוקן יפוג בעוד שנה, או אם GitHub יחזיר
שגיאה, אתה תדע על זה במייל — במקום לגלות עוד שבועיים שההתראות שוב שקטות.
כל הבעיה שהתחלנו ממנה היא כשל שקט; זה מה שהופך את התיקון עצמו ללא-שקט.

## שלב 4 — בדיקה מיידית

ב-cron-job.org לחץ **TEST RUN**.

- **תשובה תקינה:** `204 No Content` וגוף ריק. זו ההצלחה — GitHub לא מחזיר
  תוכן על dispatch מוצלח.
- `401 Bad credentials` → הטוקן לא הודבק נכון, או חסרה המילה `Bearer `
- `403` / `Resource not accessible` → לטוקן אין הרשאת **Actions: Read and write**
- `404` → שם הריפו או שם הקובץ (`alerts.yml`) שגוי בכתובת

אחר כך פתח את לשונית **Actions** ב-GitHub. תוך שניות אמורה להופיע ריצה
חדשה של "Check price alerts" עם התווית **workflow_dispatch**.

## מה קורה עם התזמון הישן של GitHub

**הוא נשאר דלוק, בכוונה.** אם GitHub כן יורה, פשוט תהיה ריצה נוספת — וזה
לא מזיק:

- `concurrency: alerts` מונע שתי ריצות חופפות
- `data/alert_state.json` זוכר מה כבר נשלח, אז אותה התראה לא תישלח פעמיים
- הריפו ציבורי, ולכן דקות ה-Actions **חינמיות וללא הגבלה**

שני מתזמנים שאחד מהם אמין = גיבוי בחינם. אין סיבה לכבות אחד מהם.

## כשהטוקן פג

Fine-grained tokens פגים. כשזה קורה, cron-job.org יתחיל לקבל `401` וישלח לך
מייל (אם סימנת את שלב הנוטיפיקציות). התיקון: ליצור טוקן חדש באותה דרך
ולהחליף רק את שורת ה-`Authorization` ב-job. שום דבר אחר לא משתנה.

## מגבלות שכדאי להכיר

- cron-job.org חינמי: מספר משימות ללא הגבלה, עד ריצה בדקה, timeout של
  30 שניות. ה-dispatch מחזיר תשובה במאות מילישניות, אז זה לא מתקרב לגבול.
- ההפעלה בפועל יכולה לאחר ב-4 עד 40 שניות מהזמן שנקבע. לא רלוונטי כאן —
  בדיקה ששמה לב לדוח בתוך שעה שלמה לא מושפעת מ-40 שניות.
- זה עדיין תלוי ב-GitHub Actions עצמם כדי להריץ את העבודה. מה שהוחלף זה
  רק המתזמן, שהוא החלק שהוכח כלא אמין.
